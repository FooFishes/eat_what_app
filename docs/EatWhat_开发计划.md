# EatWhat 开发计划

本文把开发分成七个阶段，按顺序做，每个阶段写清要做的事和做完是什么样。不排日期，也不拆到具体任务：一个阶段可以拆成多个 PR，怎么拆由做的人定。

依据：界面守设计原则，`prototype/` 是设计快照、供参考（见 `docs/EatWhat_设计与实现.md`），接口以 `docs/api.openapi.yml` 为准，代码怎么组织见 `docs/EatWhat_技术架构.md`，用哪些包、什么时候加见 `docs/EatWhat_依赖选型.md`。

| 阶段 | 做完以后 | 状态 |
| --- | --- | --- |
| 一、地基 | 工程、设计系统和页面骨架就位，三个主页面能切换 | 基本完成 |
| 二、网络层与账号 | 能注册、登录、完成学生认证 | 基本完成 |
| 三、逛起来 | 三个主页面和详情页接上真实数据，能逛、能找、能点赞收藏 | 基本完成 |
| 四、发布一道菜 | 从选店到发布走得通，照片经过调整和取色 | 基本完成 |
| 五、内测 | 测试包能交给同学用，出了问题看得到、修得快 | 进行中：正式图标和启动图 |
| 六、我的与社交 | 「我的」的子页面、他人主页、关注和设置都补齐 | 基本完成 |
| 七、上架 | 应用商店上架 | 未开始 |

## 贯穿各阶段的做法

- 每个阶段结束时，`main` 都能在 Web 上跑起来，CI 的检查和 Android、iOS、Web 构建都是绿的。
- 依赖在第一个用到它的阶段加入，同时把依赖选型表里的「状态」改成「已引入」。
- 设计里有、接口还没有的功能，在它所在的阶段照样做出界面，带「待接入」，数据先用示例（见技术架构「待接入的功能」）。接口上线后单独接上，不等阶段，见文末「接口补齐」。
- 测试跟着功能走：纯逻辑写单元测试，组件和页面写 Widget 测试，点击区域和对比度检查放进页面的 Widget 测试。
- 和接口对不上的地方（字段、权限、行为）记下来反馈给后端。每个阶段开头列了这一阶段要先对齐的事。

## 阶段一：地基

把工程、设计系统和页面骨架搭好，后面的阶段只往里填功能。这一阶段不接接口。

- **工程**：加入状态管理、路由、SVG 和代码生成这一批依赖（`material_ui`、`flutter_riverpod`、`riverpod_annotation`、`go_router`、`flutter_svg`、`build_runner`、`riverpod_generator`、`riverpod_lint`），现有代码从 `package:flutter/material.dart` 换到 `material_ui`；按技术架构建目录；CI 加上 `dart analyze` 和代码生成检查；加 `config/example.json` 和 `AppConfig`。
- **设计系统**：令牌和 `ThemeExtension`、`StageColor`、文字样式、动效常量；数字字体 Inter 子集化后打包，子集脚本入库，中文安卓内置 Noto Sans SC 子集、iOS 用苹方；78 个图标复制进 `assets/icons/`，做图标组件；基础组件 Button、Chip、Tabs、ListRow、RadioRow、Switch、SearchField、FormField、Sheet、Stage、Panel、NavBar、DishPlate、DishTile；加载占位、失败重试、空状态、「待接入」标记。Turntable、TasteCloud、MapPin、StageColorPicker 和具体页面绑得紧，放到第一个用到它们的阶段做。
- **页面骨架**：`StageScaffold`、`PlainScaffold`、`showPanel`；路由表和路径常量；三个主页面的外壳和悬浮 `NavBar`；Web 路径式 URL；返回的兜底；只在 debug 构建里出现的组件页。

参考画板：`G-Kit`、`G-Nav`、`G-Icons`、`G-Icon`，组件参考 `prototype/design-system/components/` 的说明，接口和行为以 Dart 为准。

做完是什么样：

- Web 上能看到发现、附近、我的三个空页面，`NavBar` 悬浮在下方，切换时各页的状态保留；发布按钮能打开空的发布页。
- 组件页里的组件和 `G-Kit` 对得上，按下、选中、不可用、键盘焦点几种状态都有；组件的 Widget 测试覆盖这些状态，并通过 44px 点击区域和对比度检查。
- 代码里没有直接导入 `package:flutter/material.dart` 的地方，分层方向的测试通过。

## 阶段二：网络层与账号

从这一阶段开始调真实接口。做完以后能注册、登录、完成学生认证，登录态可靠。

先和后端、设计对齐：

- 没认证的用户能看什么：设计是登录后都能逛，认证后才能发布、点赞、评论、关注；接口目前菜品的读接口（推荐、详情、列表）和餐厅详情都要求已认证，关注反而只要求登录。
- 业务码：登录失效、没有认证、需要数据跨境同意分别是哪些。统一认证的流程已经对齐（技术架构 18.1），还差失败时的跳转（现状差距 2.1）。

要做的事：

- **网络层**：加入 `dio`、`json_annotation`、`json_serializable`；做 `ApiClient`、`ApiException` 分类和业务码表、鉴权头、重试策略、`cacheFor` 和 `cancelToken`、`Page<T>`、时间和图片地址的转换，用假的适配器把每一种失败都测到。
- **会话**：`flutter_secure_storage` 存 token，启动前读出；登录重定向和登录后回到原地址；登录失效回登录页；退出登录。
- **登录和注册**：登录页（协议勾选，`url_launcher` 打开协议）、手机号验证码登录（新号码自动注册）、手机号或用户名加密码登录；发验证码前的人机验证（`webview_flutter`，Web 直接加载 JS，见技术架构 18.3）。
- **数据跨境同意**：服务端要求同意时弹一个最简的同意对话框，由用户点同意，不代用户同意（2026-11-02 改）；登录、注册和会话中的处理见技术架构「数据跨境同意」。不做单独的同意页面。
- **认证**：认证页的邮箱认证、统一认证（`flutter_web_auth_2` 的系统认证会话，Web 整页跳转），回到前台刷新认证状态；当前用户；认证拦截对话框，以及接口因为没认证拒绝时的统一处理。
- **设置页**：`G-Settings` 本身、退出登录的确认对话框、版本号（`package_info_plus`）。各子页放到阶段六。

参考画板：`G-Login`、`G-PhoneLogin`、`G-PasswordLogin`、`G-Verify`、`G-Settings`。接口：Auth、AccountConsent（同意和读政策版本）、User（`/user/info`）。

做完是什么样：

- 新号码用验证码登录即完成注册，老用户能用验证码或密码登录；杀掉 App 重开还是登录状态；token 失效时回到登录页，登录后回到原来的页面。
- 服务端要求数据跨境同意时弹出同意对话框，用户同意后登录和使用照常进行。
- 能用山大邮箱完成认证，回到 App 自动刷新；统一认证按对齐的流程在 App 和 Web 上走通。
- 没认证的用户点被限制的操作会被拦下，引到认证页。

## 阶段三：逛起来

三个主页面和详情页接上真实数据：能转着挑菜、看菜和店、在地图上找附近的店、搜店，能点赞、收藏、加标签。弱网策略在这一阶段完整落地。

先和后端对齐：推荐接口没有饭点、地点、分类参数；店铺列表没有招牌菜和图，而地图标记和列表行都要用；搜菜还没有接口。

要做的事：

- **发现**：舞台和转盘（`Turntable`：拖动跟手、吸附回弹、「换一个」、撞色顺延、舞台换色）、「就它了」进菜品详情、推荐流和分类、地点和饭点面板、搜索入口和带未读数的消息入口。插画版和实拍图版用同一套组件。`cached_network_image` 在这里加入。
- **菜品详情**：舞台、去这家店、「大家怎么说」（`TasteCloud`）、赞和收藏、分享（`share_plus`）。举报面板、全部评论、写评论带「待接入」。
- **餐厅详情**：舞台、菜单和招牌、口味标签、「导航去店里」（`url_launcher` 调起高德）、「加一道菜」（阶段四接上发布）。评分、收藏店铺、信息有误带「待接入」。
- **附近**：地图（先做的是 `flutter_map` 加天地图，2026-11-09 改为百度地图，见技术架构 14.4）、`geolocator` 定位和权限、坐标转换、`MapPin` 和商圈范围、店铺抽屉、回到我的位置。筛选面板带「待接入」。
- **搜索**：搜店、最近搜过的词（`shared_preferences`）、没找到时引到新建店。搜菜带「待接入」。
- **我的**（只做主页面）：舞台、昵称和签名、统计、上传和收藏两个网格，评论带「待接入」。
- **消息**：通知列表、分类、未读点、全部已读、点进对应的菜或人。
- **专题**：专题和往期专题带「待接入」。
- **弱网**：骨架占位、失败重试、详情页 5 分钟缓存、从列表进详情先画舞台，按技术架构「弱网与加载」逐页落实。

参考画板：`G2-Home`、`G-HomePhoto`、`G-PanelPlace`、`G-Dish`、`G-PanelTag`、`G-PanelReport`、`G-Comments`、`G-WriteComment`、`G-Detail`、`G-WrongInfo`、`G-Nearby`、`G-PanelFilter`、`G-Search`、`G-Me`、`G-Inbox`、`G-Topic`、`G-TopicArchive`。接口：Food、Restaurant（搜索、详情）、Hub、Notification、User（统计）。

做完是什么样：

- 已认证的用户打开 App 就能在发现页转着挑菜，点进菜品和餐厅详情；赞、收藏、加标签都存到了服务端。
- 附近页在 Android、iOS、Web 上都能显示底图、我的位置和附近的店，店的位置和底图对得上。
- 切换主页面不重复请求；用系统或浏览器的网络限速模拟弱网，页面先出占位，失败可以重试，有旧数据时不白屏。
- 每个「待接入」的入口都看得到，点了不发请求。

## 阶段四：发布一道菜

走通从选店到发布的整个流程。照片经过调整和取色，弱网下也能发出去。

要做的事：

- **选店**：按当前位置排的附近店（`/hub/locate` 判断所在商圈）、搜店名、选中态和「下一步：给某某加菜」。
- **新建店**：附近已有同名店的提示、拖地图选点、自动判断商圈、地址描述、可选的门头照片、建好后去加菜。
- **加菜**：`image_picker` 选图和拍照（最多 9 张）、菜名、价格、分类、口味标签和自己写的标签、发布。
- **调整照片**：拖动、缩放进圆圈和缩放滑条，`StageColorPicker`（三个推荐色和实时预览）；取色算法和用实拍图写的单元测试，对照 `G-PhotoPipeline`。画板上标「测试中」的自动去背景不做（见依赖选型「图片」）。
- **上传**：`Uploader` 的三步上传；选好照片就在后台传，显示进度、可以取消，失败的单独重传；发布后失效「我的上传」和相关列表。
- 发布和新建店要认证，没认证的在入口就被拦下。

参考画板：`G-PickShop`、`G-NewShop`、`G-AddDish`、`G-Crop`、`G-PhotoPipeline`。接口：Upload、Restaurant（新增）、Food（发布、标签）、Hub（定位）。

做完是什么样：

- 在 Android、iOS、Web 上都能拍照或选图、调整、选舞台色并发布，发布的菜出现在「我的」的上传和餐厅详情里。
- 网络断开再恢复，已经填的内容和传好的照片都还在，重试只补传没传完的。
- 取色的单元测试和设计稿的结果一致。

## 阶段五：内测

把测试包交给同学用：出了问题看得到，Dart 层的问题不用等重新发版就能修。

- **监控**：接入 `sentry_flutter`、`sentry_dio`，CI 用 `sentry_dart_plugin` 上传符号表和 source map。接入前先去 Sentry 后台作废 `legacy` 分支曾经写进 `pubspec.yaml` 的 token。
- **热更新**：接入 Shorebird。先确认它支持 `.fvmrc` 里的 Flutter 版本、国内下载补丁的速度和免费额度；`shorebird_code_push` 读补丁号；`v*` tag 的构建改用 `shorebird release`，`SHOREBIRD_TOKEN` 放 Secrets。
- **签名与分发**：Android 上传密钥（不入库，CI 从 Secrets 注入），定下安卓测试包怎么分发；iOS 签名和 TestFlight。Web 不上线，先不部署测试站（2026-11-21）。
- **应用信息**：正式图标和启动图（到时评估 `flutter_launcher_icons`、`flutter_native_splash`），中文的权限说明。
- **过一遍**：在 360 宽的安卓机、iPhone 和桌面浏览器上把前四个阶段的页面走一遍，看启动速度和转盘、地图的流畅度。

做完是什么样：

- 打 `v*` tag 会产出签名的 Android 包和 TestFlight 上的 iOS 包。
- 测试包的崩溃能在 Sentry 里看到，带版本号和补丁号；推一个补丁，已经装好的测试包能收到。

## 阶段六：我的与社交

补齐「我的」的子页面、他人主页和关注关系，以及设置的各个子页。

- **我的子页面**：编辑资料（换头像用同一套调整手势，导出 512×512 上传；昵称、签名）、我的标签（改名、删除）、标签下的菜、足迹（菜和店两类，可清空）、我的粉丝与关注。
- **他人主页和关注**：他人主页的统计和关注、回关、已互关，上传列表、屏蔽、举报带「待接入」；粉丝与关注列表，包括对方没公开时的样子。关注按设计要认证，走认证拦截。
- **设置子页**：账号与安全（认证状态、用户名、换绑手机、设置或修改密码、登录设备；注销带「待接入」）、隐私（公开关注和粉丝列表、个性化推荐、屏蔽的人）、通知（各栏目的推送开关）、关于（版本号、补丁号、协议）、反馈（文字和截图，从菜或店进入时带上它）。

参考画板：`G-EditProfile`、`G-MyTags`、`G-TagDishes`、`G-History`、`G-Follows`、`G-UserProfile`、`G-SettingsAccount`、`G-Devices`、`G-DeleteAccount`、`G-SettingsPrivacy`、`G-Blocked`、`G-SettingsNotify`、`G-SettingsAbout`、`G-Feedback`。接口：User（资料、关注、粉丝、隐私）、Food（我的标签）、History、Upload（头像）。

做完是什么样：

- 除了不做的同意页面（同意只用对话框），`prototype/screens/` 里的每一张画板都有对应的页面：有接口的功能都接上了，其余带「待接入」。
- 换头像、改资料、改标签、关注和取关都存到了服务端，相关页面上的数字跟着变。

## 阶段七：上架

- **合规**：《隐私政策》《用户协议》定稿；按国内安卓商店的隐私检测要求自查（同意前不采集个人信息、权限按需申请、列出用到的 SDK）；按各商店当时的要求准备上架材料（如 App 备案、软件著作权）。
- **商店**：提交 App Store 审核，上架选定的国内安卓商店。
- **最后一轮检查**：读屏把主要流程走一遍，减少动态效果、系统字体放大、弱网和断网各试一遍；看内测期间的崩溃率和启动速度。
- **发版流程**：定下版本号规则、打 tag 发版的步骤，以及 Shorebird 补丁的边界（只修 Dart 代码，原生和插件的改动发新版），写进文档。

做完是什么样：

- App 在 App Store 和选定的安卓商店上架。
- 发版和推补丁有固定的步骤，照着文档就能做。

## 接口补齐

设计里标「待接入」的功能，接口上线一个就接一个，不等阶段：补接口类，把 provider 从示例数据换成接口，去掉「待接入」，补测试。待接入的入口在代码里都标着 `PendingFeature`（`lib/core/env/pending_features.dart`）。评论、举报、信息有误、反馈、附近筛选、店铺评价和收藏都已接上。

2026-11-13 迁到后端 v2 后，下面几项后端删掉或暂缓了接口（等级、个性化推荐开关和注销 2026-11-14 已接上）。已经写好的页面和数据层保留，入口标「待接入」、不进入（技术架构 8.5），后端恢复后再接回：

| 功能 | 画板 |
| --- | --- |
| 专题、往期专题（后端暂缓） | `G-Topic`、`G-TopicArchive`、`G-HomeTopic` |
| 我的标签、标签下的菜 | `G-MyTags`、`G-TagDishes` |
| 口味标签投票、加标签面板（口味改成了菜自身的属性） | `G-Dish`、`G-PanelTag` |
| 推送的设备登记（通知页的栏目开关已接上） | `G-SettingsNotify`，还要先选推送 SDK（见依赖选型「推送」） |

## 发版节奏

- 每个 PR 和 `main` 的提交都由 CI 产出 Android、iOS（未签名）、Web 构建，供自己验证。
- 从阶段五开始，打 `v*` tag 出测试包；两次发版之间，Dart 层的修复用 Shorebird 补丁推给测试包。
- 阶段七之后按同样的方式发正式版，商店版本和补丁的记录写进发版文档。
