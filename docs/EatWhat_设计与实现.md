# EatWhat 设计稿与 App 的关系

> 2026-10-30 初稿。起因是讨论 `prototype/` 和 App 的一致性该怎么保证，讨论到一半发现问题出在前提上：现有文档把设计稿当成了正本。

本文说清楚三件事：设计稿在这个项目里是什么、不是什么；哪些东西要守住、哪些由 App 自己决定；以及文档和流程按这个认识改了什么。

## 1. 结论

- **产品是 App，不是设计稿。** 用户用的是 App，被真实数据和真实照片检验的也是 App。「像画板」不是目标。
- **设计稿是方向，不是规格。** `prototype/` 的任务是把风格定下来、把该想的页面想一遍。这个任务已经完成。它留下的有效资产是少数几条风格原则和一组起始值，不是 62 张画板上的每一个像素。
- **正本在 App 里。** 令牌、组件、页面排布的正本都是 Dart 代码。要改就在 App 里改，不回写 HTML，也不要求在线版先改。
- **`prototype/` 冻结。** 它是 2026-10-22 的设计快照，此后不再更新，在线版的后续改动也不同步进仓库。
- **App 的 UI/UX 有自己的参照。** 移动端和网页在交互方式、系统集成、性能约束上有大量差异，这些由平台惯例和实现经验决定，不由画板决定。

## 2. 现状：文档把设计稿当法则

改之前，文档里有这些表述：

| 位置 | 原话 | 隐含的前提 |
| --- | --- | --- |
| `AGENTS.md` | 视觉以 `prototype/` 为准 | 画板是视觉的正本 |
| `AGENTS.md` 「界面落地」 | 细节以规范为准 | 规范是法则 |
| `docs/EatWhat_开发计划.md` | 界面以 `prototype/` 为准；组件以 `components/` 为准 | 组件说明是接口规格 |
| `docs/EatWhat_技术架构.md` 11.1 | 设计更新导出后跑测试，就知道哪里没同步 | 设计先改，App 跟着同步 |
| `docs/EatWhat_技术架构.md` 21.2 | 组件和画板对齐稳定后，加 golden | golden 的基准是画板 |
| `prototype/README.md` | 设计以在线版为准。在线版改过之后，重新导出覆盖本目录 | 在线版是上游，仓库是下游 |
| `test/design/tokens_test.dart` | 设计更新导出 `tokens.json` 后跑这个测试，就知道哪些值没同步 | `tokens.json` 是正本，Dart 是副本 |

这些话单看每一句都合理，合在一起就是一个结构：**在线版 → 导出 → `prototype/` → 转写 → Dart**，设计在上游牵引，App 在下游跟随。

## 3. 为什么这个结构不对

### 3.1 改动回路的长度反了

设计稿是 Claude Design 里用对话生成的网页。改一处的回路是：对话 → 检查结果 → 导出 → 改写资源路径 → 覆盖 `prototype/` → 跑令牌测试 → 改 Dart → 再测。

App 里同一处改动：改 Dart → 测。改完就是产品本身。

把回路长的一方当正本，等于让慢的牵引快的。实际后果是两种：要么每次界面上的小调整都要走一遍长回路，开发节奏被设计工具拖住；要么大家绕开回路直接改 App，设计稿慢慢失真，而文档还写着「以它为准」，新来的人（或新开的 agent session）照着失真的东西对齐。

### 3.2 画板是网页，产品是 App

画板是在浏览器里、一个固定 390×844 的框内画出来的。它用的是网页的语言：hover、`href` 跳转、浏览器默认的滚动，数据也都是整齐好看的假数据。它不处理、也不该处理安全区、系统返回、键盘、权限弹窗、后台切换、弱网这些事。

这些不是画板的缺点，画板本来就不是干这个的。但移动端产品的体验恰恰大半在这些地方。如果 App 的目标是「和画板一致」，它们就都成了「画板没画所以先不管」。

### 3.3 一致性检查会检查错东西

按「以画板为准」做对照，查出来的会是：这个间距差 2px、这行字号不一样、这个圆角不对。查不出来的是：菜名太长时舞台排版垮了、无图时盘子里是空的、弱网时转盘转不动、从后台回来页面是白的。前一类偏差对用户几乎没有影响，后一类直接决定好不好用。

### 3.4 对 agent 协作尤其有害

「以 X 为准」这种措辞会被字面执行。每个 session 读到 `AGENTS.md` 都会去抠画板，遇到画板没覆盖的情况倾向于停下来问，或者按画板的假数据做一个只在假数据下好看的页面。原则讲清楚了，agent 反而能做出合理的判断。

## 4. 重新定位

### 4.1 设计稿是什么

- 风格探索的产出。从 A–I 九个候选收敛到 G，这个过程确定了产品的样子。
- 页面清单的一次完整演练。62 张画板把该有的页面、面板和状态都想了一遍，App 的路由表和开发计划的范围来自这里。
- 一组起始值。`tokens.json` 的颜色、间距、字号是 App 令牌的初始版本。

### 4.2 设计稿不是什么

- 不是实现规格。画板上的像素、行高、具体排布是参考，不是验收标准。
- 不是持续维护的上游。仓库里的 `prototype/` 是 2026-10-22 的快照，此后不变。
- 不是回写目标。App 做出的设计决定不往 HTML 里写。

### 4.3 一句话

**App 具有设计，而不是设计拥有 App。** 设计规范是 Guide：写清楚产品的性格和为什么这样，其余交给做的人判断。

## 5. 三个层次：守住的、参考的、App 自己的

### 5.1 守住的：风格的性格

这些是产品的辨识度，守住了别人一眼就知道是这个 App。偏了算 bug，不需要讨论：

| 原则 | 出处 |
| --- | --- |
| 舞台跟着主角换色：菜按取色，店按品类；只有 9 个 `stage-*`，每个带自己的文字色，深浅写死 | 规范「颜色」、产品 4.7 |
| 没有品牌主色，主操作用 `ink` 实心；`warn` 只用来说该做什么，且配文字 | 规范「颜色」 |
| 中文安卓用内置的 Noto Sans SC、iOS 用苹方，主角 800（iOS 苹方最粗 Semibold，安卓按它校正了字重）；数字只用 Inter，中文永远不用 | 规范「字体」 |
| 选中态靠字重，不靠颜色；分类栏的选中项另压一道舞台色的记号笔 | 规范「字体」「状态」 |
| 能点的都是胶囊；食物和头像永远是正圆，`DishPlate` 带白色盘沿；缩略图方圆角 | 规范「间距与圆角」「图片」 |
| 阴影克制：只用在盘子、悬浮导航、地图标记、地图上的抽屉和按钮，不给卡片加投影 | 规范「间距与圆角」 |
| 图标只用 MingCute 官方一套（空心为主），`currentColor`，只有赞过、收藏过和底部导航选中的标签用实心，不用 emoji | 规范「图标」 |
| 三种页面结构：有主角（菜、店或人）的页面用舞台加抽屉；列表和操作用白底；临时选择用底部面板 | 规范「页面结构」 |
| `NavBar` 只在发现、附近、我的三个页面 | 规范「页面结构」 |
| 文案：引导像同学说话；提示和报错用规范短句；不用 emoji 和感叹号（登录页的动画表情和评论的表情回应除外，用图片）；专题标签用「」 | 规范「内容与语气」 |
| 取色只看圆圈内像素，按饱和度加权，吸附到最近的 `stage-*`，不可靠时用分类默认色 | 规范「图片」 |
| 转盘吸附带回弹，舞台换色 500ms；减少动态效果时停掉自动动画 | 规范「动效」 |
| 点击区域不小于 44px，对比不低于 4.5:1，能滑的都有按钮替代 | 规范「无障碍」 |

`AGENTS.md` 「界面落地」一节是这张表的浓缩版，写界面前读那里就够了。规范 README 是这些原则的展开和示例，想知道为什么这样时再看。

### 5.2 参考的：具体数值和排布

令牌的具体值、画板上某页怎么分组、某行怎么排、抽屉压舞台多少像素。这些从 `prototype/` 起步，之后在 App 里按实际效果调。调了不用回写，不用解释，不用记录偏差。

判断标准只有一个：改完之后 5.1 的原则还守着吗。守着就行。

### 5.3 App 自己的：移动端产品该有的样子

移动端 App 和网页是两种产品形态。画板没有、也不可能替 App 回答的问题很多，它们的参照是平台惯例（Apple 的 Human Interface Guidelines、Android 的 Material 指南）、Flutter 的常规做法和做移动端产品的常识。下面是方向性的提醒，不是清单；具体做法在技术架构和各阶段的实现里定。

- **输入方式不同。** 触屏没有 hover，有按下、长按、滑动、双指缩放；手指比鼠标粗，点击区域、间距、可误触的位置都要重新想。Web 端又要兼顾鼠标和键盘。
- **导航是系统的一部分。** 返回手势、系统返回键、页面栈、模态和底部面板的层级，用户在别的 App 里已经形成习惯，照着平台惯例做，不自己发明。
- **屏幕不是一个固定的框。** 安全区、状态栏、键盘弹起、横竖屏、折叠屏、系统字号放大、宽屏，都会改变可用空间。
- **App 有生命周期。** 切到后台再回来、被系统杀掉后重开、来电打断、权限弹窗，每一种都要有合理的表现。
- **网络和数据是不可靠的。** 弱网、断网、超时、重试、缓存、分页；数据会比假数据长、比假数据少、比假数据怪。
- **状态比画板多。** 加载、失败、空、没网、拦截、待接入，每个页面都有，而且相互组合。
- **反馈的方式不同。** 触感反馈、轻提示的时机和位置、加载指示，和网页的习惯不一样。
- **性能是体验的一部分。** 列表滚动掉帧、图片解码占内存、动画在低端机上卡顿，这些在浏览器里的画板上看不出来。
- **无障碍是系统能力。** 屏幕阅读器、动态字号、减少动态效果，要接到系统的设置上，不是自己做一套开关。

这些都不是「和画板一致不一致」的问题，是 App 本来的工作。

## 6. 正本移到 App 以后

- **令牌**：Dart 里的令牌是正本。`tokens.json` 是起点，不再更新；和它逐项比对的测试已删。
- **组件**：`prototype/design-system/components/` 的说明是参考，Flutter 组件的接口和行为以 Dart 代码为准。组件页（`G-Kit` 对应的 Kit 页）是看组件实际效果的地方，应该用真实数据的样子来摆。
- **Golden 测试**：基准是 App 自己的输出，目的是防止组件回归，不是和画板比对。
- **图标和插画**：已从快照复制进 `assets/`，以后新增的直接加进 `assets/`。
- **`prototype/` 目录**：冻结，保留。画板仍是构思页面时最快的参考，页面清单也还有用。以后需要构思新页面可以再用设计工具做，产出当作输入材料，不承担回写义务。
- **设计规范 README**：随目录一起冻结。App 侧的界面决定写在技术架构里。
